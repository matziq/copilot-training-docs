3.1 Analyze, monitor, and tune AI-powered business solutions

Pick the right monitoring tool for each layer, read the metrics correctly, and turn telemetry into a concrete tuning action.

An architect does not monitor “the agent” as a single box. Every solution has layers: the conversation experience, the orchestration and tools, the model, the grounding data, and the platform it runs on. Each layer has a different tool that sees it best. Exam scenarios usually describe a symptom and ask which tool or which change gets you to the root cause fastest.

Key agent metrics

Know what each metric means and, more importantly, what a bad value usually points to. In Copilot Studio, a session becomes engaged when it triggers a custom topic or enters a system topic such as Escalate, Fallback, or Conversational Boosting. Resolution, escalation, and abandonment are measured against engaged sessions.

MetricDefinitionA bad value usually means
Engagement rateShare of sessions that became engaged.Users don’t know what the agent can do, or topic and knowledge coverage has gaps.
Resolution rateShare of engaged sessions that ended resolved, either confirmed by the user or implied by the flow.Answers are wrong, incomplete, or the agent can’t complete the action the user needs.
Escalation rateShare of engaged sessions handed to a human.Missing topics, missing actions, or policy-required handoffs. Not always bad—some escalation is by design.
Abandonment rateShare of engaged sessions that ended without resolution or escalation after a period of inactivity.Confusing conversation design, slow responses, loops, or excessive questions.
CSATAverage customer satisfaction score from the end-of-conversation survey.Perceived quality issues; read alongside comments and transcripts.
LatencyTime to first response and total response time, often tracked as median and P95.Large prompts, too many sequential tool calls, slow connectors, or an oversized model.
Token usageInput and output tokens per run or per conversation.Over-long instructions, too much retrieved context, verbose output, or retry loops—all of which drive cost.
GroundednessHow well a response is supported by the retrieved source content.Hallucination risk: weak retrieval, stale or poor-quality knowledge, or instructions that allow answering from general knowledge.
Thumbs up/down and commentsExplicit user reactions captured per response.The fastest qualitative signal for prioritizing the backlog.

Analyze the backlog and user feedback

Feedback is only useful when it becomes prioritized work. A practical loop looks like this:

  1. Collect: thumbs up/down reactions, CSAT surveys, free-text comments, transcripts, escalation reasons from human representatives, and support tickets about the agent.
  2. Cluster: group issues by theme (missing knowledge, wrong answer, failed action, tone, latency). AI-based tools help here—Copilot Studio surfaces themes and improvement suggestions from analytics, and you can use generative AI to summarize and categorize large volumes of transcripts or comments.
  3. Size: weight each cluster by volume and by business impact (for example, revenue-bearing or compliance-sensitive flows first).
  4. Fix: add or correct knowledge, refine instructions, add a topic or tool, adjust the model or retrieval settings, or route to a human by design.
  5. Verify: rerun your regression test set and evaluations, then watch the same metric after release.
Architect mindset

Tie every tuning change to a metric you expect to move. “Add a returns-policy knowledge source to lift resolution rate for the Returns theme” is a plan. “Make the agent better” is not.

Interpret telemetry: symptom to fix

SymptomLikely causeTuning action
Low engagement, high Fallback hitsUsers ask about things the agent has no topic or knowledge for.Mine Fallback utterances, add knowledge sources or topics, improve the greeting so users know the scope.
High escalation on one topicTopic can’t finish the task (missing action, missing data, or authentication gap).Add a tool, connector, or agent flow; verify authentication; redesign the topic.
High abandonment mid-conversationToo many questions, loops, or long waits.Use slot filling and entity extraction, reduce turns, shorten tool chains, set user expectations.
Fluent but wrong answers; low groundednessRetrieval returns irrelevant or stale content, or the model fills gaps from general knowledge.Clean and refresh grounding data, tighten instructions to answer only from sources, improve chunking and indexing.

Exam traps
  • Resolution and escalation rates are calculated from engaged sessions, not all sessions.
  • A high escalation rate is not automatically a failure—regulated processes may require human handoff.
  • Copilot Studio analytics answers “how is this agent doing.” The Microsoft 365 admin center answers “how is Copilot adoption going.” Purview answers “was data handled correctly.”
  • When the question says “see which step in the agent’s chain failed,” the answer is tracing, not a dashboard KPI.

3.2 Manage the testing of AI-powered business solutions

Design a repeatable test process with measurable pass criteria for agents and custom models.

Generative AI is non-deterministic, so testing shifts from “exact expected output” to “output meets criteria.” You still need traditional functional tests for flows, connectors, and integrations, but you add evaluation sets scored by metrics, often using an AI judge plus human review.

Test process for agents

1. Define criteria

Translate requirements into measurable targets: task completion, groundedness threshold, maximum latency, zero critical safety failures, escalation behavior for out-of-scope requests.

2. Build test sets

Cover happy paths, edge cases, ambiguous phrasings, multi-turn conversations, out-of-scope questions, adversarial prompts, and each user role or persona.

3. Run and score

Use the Copilot Studio test pane for interactive debugging and agent evaluation with test sets for batch runs; use Foundry evaluations for pro-code agents and models.

4. Human review

Subject matter experts review a sample, especially low-scoring and high-risk cases, to calibrate the automated judge.

5. Gate the release

Make evaluation results a pipeline gate. A release proceeds only when scores meet thresholds and show no regression against the current production baseline.

6. Monitor in production

Keep evaluating sampled production traffic so drift in data, models, or user behavior is caught early.

Test types and metrics

Test typeWhat it provesTypical metrics
Functional / topic testsTriggers fire, variables fill, branches route correctly.Pass/fail per scenario, trigger accuracy.
Quality evaluationAnswers are correct and useful.Groundedness, relevance, coherence, fluency, similarity to a reference answer.
Agent and tool evaluationThe agent picks the right tool with the right inputs and finishes the task.Intent resolution, task adherence, task completion, tool call accuracy.
Safety and red teamingThe agent resists misuse and doesn’t produce harmful content.Defect rate for hate and unfairness, sexual, violence, self-harm, jailbreak and indirect attack success rate.
Performance and loadThe solution meets response targets at expected volume.P50/P95 latency, throughput, throttling errors, cost per conversation.
User acceptance testingBusiness users agree the agent does the job.Task success, CSAT from pilot users, qualitative feedback.

Foundry evaluations

Microsoft Foundry evaluation applies evaluators to a test dataset, to responses generated from test inputs, or to production traces. Results show aggregate scores and per-row explanations so you can compare versions.

Quality evaluators

  • Groundedness: is the response supported by the provided context?
  • Relevance: does it address the user’s question?
  • Coherence: is it logically organized and consistent?
  • Fluency: is the language natural and grammatically correct?
  • Similarity and NLP metrics (for example F1, BLEU) when you have reference answers.

Safety and agent evaluators

  • Risk and safety: hate and unfairness, sexual, violence, self-harm, protected material, indirect attack.
  • Agent behavior: intent resolution, task adherence, task completion.
  • Tool use: tool call accuracy and related evaluators.
  • Combine them: a RAG agent needs retrieval and groundedness plus safety; an action-taking agent needs tool and task evaluators plus safety.

Validation criteria for custom AI models

When the solution includes a custom or fine-tuned model (for example a classification model or a fine-tuned small language model), define acceptance criteria before training starts:

  • Baseline: compare against the current process, a rules-based approach, or the base model without tuning. A custom model must beat the baseline by enough to justify its cost.
  • Holdout data: keep a test set the model never sees during training or tuning, drawn from the same distribution as production data. Never report results on training data.
  • Precision: of the items the model flagged, how many were correct. Prioritize when false positives are expensive (for example, blocking legitimate invoices).
  • Recall: of the items that should have been flagged, how many the model caught. Prioritize when misses are expensive (for example, fraud or safety cases).
  • F1 score: the harmonic mean of precision and recall; a single number when both matter.
  • Fairness and robustness: check performance across user segments, languages, and noisy inputs.
  • Operational criteria: latency, cost per call, and model size relative to the deployment target.

Copilot prompt best practices

Good test prompts and good production instructions follow the same rules. A clear prompt includes a goal, context, expectations for format and tone, and sources to use. Beyond that:

  • Be specific and give examples of the desired output.
  • Tell the model what to do, not just what to avoid.
  • Break complex work into steps and iterate in conversation.
  • For agent instructions, state scope, refusal behavior, and when to hand off to a human.
  • Version prompts and instructions with the solution so tests can be rerun against a known state.

End-to-end testing across Dynamics 365 apps

Many business processes cross app boundaries. Lead-to-cash may start in Dynamics 365 Sales, continue to an order in Supply Chain Management, and finish with invoicing in Finance; a service case may trigger a field service work order. An end-to-end test plan should:

  • Follow a full business process from trigger to outcome, including the Copilot or agent steps inside each app.
  • Use realistic, non-production data that is consistent across the apps (same customers, products, and IDs).
  • Test the integration points: dual-write or virtual tables, Power Automate flows, connectors, and agent handoffs.
  • Run under real security roles so each step proves the user or agent only sees the data it should.
  • Include failure paths: unavailable connector, rejected approval, or a human taking over from the agent.
  • Automate regression where possible (for example, the Regression Suite Automation Tool for finance and operations apps and Power Apps Test Engine for model-driven and canvas apps).

Generating test cases with Copilot

Copilot and other generative AI tools speed up test design: ask them to produce varied user utterances for each topic, edge cases, multi-turn scripts, adversarial prompts, and synthetic data records. Copilot Studio can also generate test sets for agent evaluation from the agent’s knowledge and topics. The architect’s strategy should include guardrails:

  • Have subject matter experts review and approve generated cases and expected answers.
  • Use synthetic or masked data; don’t paste production personal data into prompts.
  • Mix generated cases with real (anonymized) user transcripts so coverage reflects how people actually talk.
  • Store test sets with the solution so they version alongside the agent.
Exam traps
  • Evaluating on the same data used to tune the model inflates scores. The answer is always a separate holdout set.
  • “Missing fraud is unacceptable” points to recall. “Analysts are drowning in false alarms” points to precision.
  • Groundedness measures support by the provided sources; relevance measures whether the answer addresses the question. An answer can be relevant but ungrounded.
  • The test pane is for interactive debugging; it isn’t a regression strategy on its own.

3.3 Design the ALM process for AI-powered business solutions

Move agents, models, and data through environments in a controlled, repeatable, and auditable way.

Application lifecycle management (ALM) governs a solution from idea through development, testing, deployment, operation, and retirement. For AI solutions, ALM has to cover four things together: the agent and app components, the models, the prompts and instructions, and the data that grounds or trains them.

Power Platform and Copilot Studio ALM building blocks

Building blockPurposeRemember
SolutionsContainers that package agents, topics, flows, connectors, tables, environment variables, and connection references for transport.Build in a custom solution with your own publisher prefix, not the default solution.
Unmanaged solutionThe editable form used in development.Lives in dev and in source control.
Managed solutionLocked, versioned package deployed to test and production.Deploy managed downstream; remove it cleanly by uninstalling. Don’t edit directly in production.
Environment variablesValues that change per environment (URLs, site addresses, feature flags, Key Vault secret references).Read-only to the agent at run time; set the value per target environment during deployment.
Connection referencesPointers that let components use a connection without hard-binding to one user’s credentials.Map to the right connection (often a service account or service principal) in each environment.
Power Platform pipelinesIn-product, admin-governed deployments from dev to test to prod.Easiest path for makers; supports approvals and pre-deployment steps. Target environments must be managed environments.
Azure DevOps or GitHub ActionsPro-code CI/CD with Power Platform Build Tools or the Power Platform CLI.Choose when you need source control, branching, automated tests, and custom gates.

Environment strategy

Development

Makers build in unmanaged solutions. Use personal developer environments or a shared dev environment per project. Keep test data synthetic.

Test / UAT

Managed solution only. Run evaluations, end-to-end tests, and user acceptance with production-like (but protected) data.

Production

Managed solution only, deployed through a pipeline. Changes come from source, never from direct edits.

Managed environments add governance on top: sharing limits, solution checker enforcement, usage insights, IP firewall and other security controls, and the ability to act as pipeline targets. Combine them with environment groups and rules to apply consistent policy across many environments.

ALM for Copilot Studio agents, connectors, and actions

  • Create the agent inside a custom solution from day one; add required objects (topics, flows, custom connectors, environment variables) before export.
  • Parameterize anything environment-specific: knowledge source URLs, API endpoints, Application Insights connection strings, and channel display name suffixes all belong in environment variables.
  • Custom connectors and their connection references travel in the solution; credentials do not. Set up connections in each environment.
  • Agent flows and Power Automate cloud flows used as actions should be solution-aware so they deploy with the agent.
  • Add a pre-deployment approval or automated review (solution checker, evaluation gate) to the pipeline stage before production.
  • After deployment, publish the agent in the target environment and confirm channel configuration and authentication settings.

ALM for Foundry Agent Service and custom models

Foundry agents

  • Keep agent definitions (instructions, tools, model deployment, knowledge connections) as code in source control.
  • Use separate Foundry projects or resources per environment, deployed with infrastructure as code (Bicep or Terraform).
  • Version agents and prompts; record which model version each agent version uses.
  • Run Foundry evaluations in CI/CD and block promotion if quality or safety scores regress.
  • Use managed identities and Key Vault rather than embedding keys.

Custom and fine-tuned models

  • Versioning: every model version links to its training data version, code, hyperparameters, and evaluation results.
  • Registries: store approved model versions in a registry so they can be shared and promoted across workspaces and environments.
  • Deployment strategy: deploy a new version alongside the old (blue-green or a staged slot) and shift traffic gradually; keep rollback ready.
  • Evaluation gates: promotion requires passing holdout metrics and safety evaluation.
  • Base model updates: plan for model version retirement; pin versions and retest before upgrading.

ALM for data used in AI models and agents

  • Treat grounding content and training data as versioned assets: know which version of a knowledge base or dataset an agent or model was tested with.
  • Promote reference and configuration data with tools such as the Configuration Migration tool or data packages rather than manual entry.
  • Use masked, synthetic, or subset data in non-production environments; respect the same residency and sensitivity rules as production.
  • Automate index refresh and data quality checks, and include them in the pipeline so stale data doesn’t silently degrade answers.
  • Record lineage so you can trace an answer or prediction back to the source data that produced it.

Exam traps
  • Production gets managed solutions. If a choice suggests exporting unmanaged to production, it’s wrong.
  • Environment variables hold values; connection references hold connections. Secrets belong in Azure Key Vault, referenced by a secret-type environment variable.
  • Power Platform pipelines require managed environments as targets.
  • Don’t build in the default solution or the default environment for anything you plan to promote.
  • For pro-code agents, the “pipeline gate” answer is an automated evaluation run with thresholds, not a manual chat test.

3.4 Design responsible AI, security, governance, risk management, and compliance

Apply Microsoft’s responsible AI principles and layer identity, data, model, and platform controls around every agent.

Microsoft Responsible AI Standard: six principles

PrincipleWhat it asksHow it shows up in a design
FairnessAI systems treat people equitably.Evaluate results across demographics and segments; remove biased features; review automated decisions.
Reliability and safetySystems perform consistently and safely, including in unexpected conditions.Evaluations, content filters, fallbacks, human handoff, monitoring, and rollback plans.
Privacy and securitySystems protect data and resist attack.Least privilege, encryption, sensitivity labels, DLP, data minimization, prompt attack defenses.
InclusivenessSystems empower and engage everyone.Accessible channels, multiple languages, voice options, and plain-language responses.
TransparencyPeople understand the system’s capabilities and limits.Disclose that users are talking to AI, cite sources, publish limitations, explain decisions.
AccountabilityPeople remain accountable for AI systems.Named owners and sponsors, approval workflows, impact assessments, audit trails, and a Center of Excellence.

Security for agents

Identity and authentication

  • Authenticate users with Microsoft Entra ID so the agent knows who is asking and can apply their permissions.
  • Microsoft Entra Agent ID gives agents their own identities in the directory, so they can be inventoried, governed, assigned a sponsor, covered by Conditional Access, and disabled like any other identity.
  • Prefer managed identities and federated credentials to stored secrets.
  • Decide deliberately between acting on behalf of the user (user’s permissions) and acting as the agent (its own permissions, typical for autonomous agents).

Least privilege and connector governance

  • Grant agents only the scopes, tables, and actions they need; review access periodically.
  • Data policies (DLP) in the Power Platform admin center group connectors into business, non-business, and blocked, and can restrict specific actions or endpoints.
  • Govern custom connectors and MCP servers the same way: approve, classify, and restrict.
  • Control who can create and share agents with managed environments, sharing limits, and environment security groups.
  • Require human approval for high-impact actions (payments, deletions, external communications).

Governance with Microsoft Purview

  • Sensitivity labels: Microsoft 365 Copilot and agents respect labels and permissions on content; labeled content keeps its protection, and responses can inherit the most restrictive label of their sources.
  • Data loss prevention: Purview DLP can restrict how Copilot processes items with specific labels or sensitive information types.
  • Audit: Copilot and agent interactions are captured in the unified audit log for investigation.
  • DSPM for AI: Data Security Posture Management for AI shows how AI apps and agents use sensitive data, flags oversharing risks, and offers one-click policies.
  • Retention, eDiscovery, and Communication Compliance: apply to Copilot prompts and responses for legal and regulatory needs.

Model security and AI vulnerabilities

ThreatWhat happensMitigation
Direct prompt injection / jailbreakA user crafts input to override system instructions or bypass safety rules.Prompt Shields for user prompt attacks, content filters, strong system instructions, output validation.
Indirect prompt injectionMalicious instructions hide in documents, emails, or web pages the agent retrieves.Prompt Shields document attack detection, spotlighting to mark external content as lower trust, least-privilege tools, human approval for actions.
Harmful contentThe model generates hate, sexual, violent, or self-harm content.Content filters with configured severity thresholds on input and output; safety evaluations before release.
Data exfiltration and oversharingThe agent reveals data the user shouldn’t see.Permission-trimmed retrieval, sensitivity labels, DLP, restricted knowledge scope.
Training data poisoningTampered tuning data degrades or backdoors a model.Controlled access to datasets, data validation, lineage, and approval before training.
Model theft or tamperingModel artifacts or endpoints are accessed or changed without authorization.Private endpoints, RBAC on registries and deployments, managed identities, Defender for Cloud AI threat protection.
Excessive agencyAn agent takes harmful actions because it has too many permissions.Least privilege, scoped tools, approval steps, rate limits.

Data residency and movement

Copilot Studio and Power Platform generative AI features rely on Azure OpenAI and related services that may not be hosted in every geography. For environments outside the United States, a Power Platform or Dynamics 365 administrator may need to allow data movement across regions in the environment’s Generative AI features settings in the Power Platform admin center. Points to know:

  • The setting is per environment and requires administrator consent to the terms.
  • Data that already moved while the setting was on isn’t pulled back by turning it off.
  • Related settings, such as Bing search, depend on data movement being allowed where the checkbox is shown.
  • For Foundry, choose the region and deployment type deliberately: global and data zone deployments can process data outside a single region, while regional (standard) deployments keep processing in that region.
  • Document residency requirements during planning; they constrain which features and regions you can use.

Access controls on grounding and tuning data

  • Ground on sources that enforce user permissions (SharePoint, Dataverse security roles, Azure AI Search with security trimming) so users only receive answers from content they can already access.
  • Fix oversharing at the source before broad rollout; an agent surfaces whatever permissions already allow.
  • Restrict who can read, change, or export tuning datasets with Azure RBAC, and keep them in storage with private networking and encryption.
  • Separate duties: data stewards approve datasets; ML engineers train; release managers promote.

Audit trails for model and data changes

  • Version and log every change to prompts, instructions, models, and datasets, including who approved it.
  • Use Purview audit for Copilot and agent activity, Dataverse auditing for record and configuration changes, and Azure activity logs for resource changes.
  • Keep evaluation results with each release so you can show the evidence behind a go-live decision.
  • Route logs to a central workspace (Log Analytics or Microsoft Sentinel) for retention and investigation.
Exam traps
  • “Instructions hidden in an uploaded document” is indirect prompt injection; the control is Prompt Shields document detection plus spotlighting, not just a stricter system prompt.
  • Turning off cross-region data movement doesn’t reverse data that already moved.
  • Agents don’t bypass permissions; oversharing is a permissions problem to fix at the source.
  • Match the principle: biased loan approvals = fairness; disclosing AI use = transparency; named owner and approvals = accountability.
  • DLP data policies in the Power Platform admin center govern connectors; Purview DLP governs sensitive content. Know which one the scenario needs.
Defense in depth

No single control is enough. A secure agent design layers identity (Entra ID and Agent ID), platform governance (managed environments and DLP), data protection (Purview labels and DLP), model protection (content filters and Prompt Shields), human oversight, and monitoring with audit.
